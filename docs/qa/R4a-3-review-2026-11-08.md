## Security review (security-reviewer)

No privilege-escalation path. Every mint, list, revoke and member-remove path gates on `jc_assert_admin('community')`. An events grant satisfies only events. The new helpers are not callable. Tokens are unchanged: 144-bit, stored as sha256, single use, failing uniformly with `BAD_LINK`.

| # | Sev | Finding | Disposition |
|---|---|---|---|
| S1 | **H** | **Open links outlive their maker.** A hostile admin pre-mints community links, gets removed, and redeems one or has an accomplice do it. They are root again. | **Fixed, two layers.** (a) `jc_module_admin_accept` now raises `BAD_LINK` unless the link's maker **is still a community admin** (`jc_community_admin_is`, the same two sources as the guard). ## Decisions recorded

- **Last admin.** Community admins are distinct people with a per-person community grant or an active community code unlock. Removing one (revoke `community`, or member-remove) that would leave 0 raises `LAST_ADMIN`. A community admin may remove themselves only while another remains. Account deletion, `jc_admin_exit` and the code lapse are not guarded.
- **Owner.** `is_owner` is **not** counted and gets no admin rights: it is platform-wide and only reads the feedback inbox. The break-glass is the owner using the Supabase SQL editor (runbook in architecture.md).
- **Lapse.** Per-person community and events grants **don't lapse**. The list flags `idle` after 90 days unused.
- **Codes.** They keep working. Retirement comes after R4b-1. Runbook in the PR and architecture.md.
