# R5c review — pet photos (residents) — 2026-11-12

Plan: `docs/plans/R5-pets.md` (R5c row). Server live since S4 / R5a and unchanged: `jc_pet_photo_begin` (server picks
`community/pet/<random>.<ext>`, PHOTO_PENDING 60 s, 20 uploads / user / day) → upload to the private `pet-photos`
bucket (2 MB, jpeg/png/webp; INSERT only at the caller's own pending path < 15 min) → `jc_pet_photo_commit` (object
must exist with an image mimetype). Reads: SELECT policy = same-community member, module on, pet active, current path.

Tier: screen logic + security (Storage, CSP). Client only — no migration. Reviewers: `security-reviewer`, `code-reviewer`.

## What shipped

- Add / Edit a pet: **Photo** — Add Photo / Change Photo, preview, "Photo ready — it's added when you save", and who
  sees it ("Neighbors in your community can see this photo. Keep people, faces, house numbers and car plates out of
  it. The photo's location data is removed before it's sent; a replaced photo is deleted within a day.").
- Shrunk on the phone: FileReader → `<img>` → canvas ≤ 1280 px → JPEG 0.82 (EXIF rotation applied; EXIF/GPS not
  carried; the original file is never sent). Refused before reading: not an image type, > 25 MB; after decoding:
  > 50 MP, output < 1 KB (blank) or > 2 MB.
- Save = `jc_pet_save` → begin → upload (raw bytes, `image/jpeg`, `upsert:false`) → commit. A photo failure never
  loses the details: "{n} is saved, but the photo didn't upload: {why}".
- Shown as a round thumbnail on list cards and large on the pet page; signed URLs (1 h, one batch per redraw for
  unseen paths, re-signed 5 min before expiry, one fresh signing after a load error); the paw stays otherwise.
- CSP (`pets/index.html`): `img-src` + `https://qrpxfssdeeuzmsmlbtbu.supabase.co/storage/v1/object/sign/pet-photos/`
  (path-scoped, not the whole origin). Other pages show no photos — unchanged.

## Security review (`security-reviewer`) — PASS

| # | Sev | Finding | Disposition |
|---|---|---|---|
| M1 | Med | Help text didn't say who can see a photo or what it can reveal | **Fixed** — `pt_photo_who` (EN + AR) under the photo field; per-feature disclosure, opt-in |
| M2 | Med | No "remove photo" — only Change | **Deferred → Zee** — the server has no remove RPC; needs a small migration (`jc_pet_photo_remove`: retire current, clear `photo_path`). Change works; replaced photos are purged within a day |
| L1 | Low | `img-src` allowed the whole Supabase origin | **Fixed** — path-scoped to `/storage/v1/object/sign/pet-photos/` |
| L2 | Low | Huge files / bitmaps can hang the tab; exceptions in `onload` not caught; SVG allowed | **Fixed** — 25 MB / 50 MP caps, try/catch → "couldn't be read", type allowlist (jpeg/png/webp/heic/heif/gif) |
| L3 | Low | Signed URLs are 1-h bearer links | **Accepted** — never shown as text; page is `no-referrer`; pet photos |
| L4 | Low | Dead signed URLs never retried | **Fixed** (same as code M1) |
| I1 | Info | Commit trusts the client-declared mimetype; nosniff on Storage unverified | **Accepted / noted** — served only into `<img>` to members holding a signed URL; a magic-byte check would be server-side (backlog) |

XSS: none (`photo_path` escaped into an attribute, read back via `dataset`; data URL generated by canvas and escaped;
signed `<img>` built via DOM with an origin-prefix check). Path control: client uses the server's path; the INSERT
policy enforces it anyway.

## Code review (`code-reviewer`) — APPROVE

| # | Sev | Finding | Disposition |
|---|---|---|---|
| 1 | Med | Signed URLs never refreshed after expiry (long-open page → paws forever) | **Fixed** — expiry kept per URL, re-signed 5 min early; one fresh signing after an `<img>` error; test with the clock moved 56 min |
| 2 | Med | Save during an in-flight shrink saved without the photo, silently | **Fixed** — Save disabled + submit refused while preparing; test holds the shrink |

| 6 | Low | Preview data URL re-parsed on every redraw | **Accepted** — ~300 KB, only on the edit form |
