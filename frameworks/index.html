Frameworks

Five frameworks for making change actually work.

The methods I use, written down. Each one is a sequence, because in operations the order matters more than the parts.

The Operations Stack

Operations infrastructure has to be built in a specific order. Skipping the lower layers to chase visible wins at the top, such as dashboards and AI tooling, is why most operational investments fail.

  1. Process design. How the work is supposed to run, written down.
  2. Data governance. One definition and one source for each number.
  3. Intake and ownership. One way in for requests, and a named owner for each.
  4. Automation and tooling. Only once the three layers below are solid.
  5. Reporting and intelligence. High-performance teams build it last.

Use it when: a dashboard or AI project has stalled, or the numbers in it are not trusted.

The Improvement Stack

Improvement work fails when a team jumps straight to solutions. Solving before diagnosing produces an expensive answer to the wrong question.

  1. Current state documentation. Map what actually exists before designing anything.
  2. Gap and root cause analysis. Find the real problem, which is rarely the assumed one.
  3. Future state design. Design the fix for the cause you found.
  4. Stakeholder alignment and change planning. Agree who changes what, and when.
  5. Control and continuous improvement. Measure whether the change held.

Use it when: something is clearly broken and everyone already has a favorite fix.

The Visible Value Loop

Customer success is architecture, not effort. Value has to be visible to the client in their own data, not narrated to them in a quarterly review. When it is, renewals stop being negotiations.

  1. Outcome re-validation. Sales defines success, client success re-validates it, data commits to it.
  2. Instrumented execution. The system carries the work so the manager can carry the client.
  3. Visible value. The client sees results in their own data, in real time.
  4. Attentive partnership. The manager is a product expert, not a traffic controller.
  5. Earned expansion. Growth comes from proven results, and starts the next turn of the loop.

Use it when: renewals depend on persuasion, or expansion sits in a separate sales motion.

The Compounding Deal Framework

Most acquisition programs run each deal as an isolated transaction, so nothing gets easier. The program is the asset, not the deal. Compounding shows up as smaller surprises, not faster deals.

Three preconditions: integration planned during diligence, a thesis that can be measured and proven wrong, and a lessons loop with a named owner.

  1. Thesis. Why this deal, stated so it can be tested.
  2. Architecture. How the two companies will run as one.
  3. Execution. One plan, named owners, visible risks.
  4. Proof. Did the thesis hold, and what did we learn.

Use it when: a second or third acquisition is coming and the last one is still not fully integrated.

The Leadership Contract

Most leadership commitments run in one direction. I write mine down as a contract with obligations on both sides, because a contract only works if both parties can name a breach.

  • What I commit to: removing roadblocks, the tools and resources to do the job properly, structural investment in growth, specific public recognition, honest and timely feedback, and clear expectations measured fairly.
  • What I ask in return: own the work end to end, no surprises, learn and use AI, bring the “so what” to every update, execute, and manage up.

Use it when: taking over a team, or when trust between a leader and a team has worn thin.
